# project-context-template 改訂設計（タスク台帳・議事録フロー・meeting-minutes skill の更新）

analysis-template-dev で 9 月に育った「タスク台帳を正本にし、議事録の表は当日の記録に絞る」運用を、project-context-template のハーネス（AGENTS.md・雛形・運用ガイド・lint）と Kyo1M/skills の `meeting-minutes` skill に取り込む。タスクはリポジトリ内の台帳とタスクファイルだけで管理し、GitHub Issue などの外部ツールとは連携しないので、起票・Issue 同期の仕組みと task 系 skill は持ち込まない。実装は 3 単位に分ける。

## 1. 現状確認

### 1-1. 関係する 4 リポジトリ

| リポジトリ | 役割 | 情報管理の現在地（2026-09-25） |
|---|---|---|
| `project-context-template`（本リポジトリ、Kyo1M） | 汎用のプロジェクト情報管理テンプレート。Claude Code / Codex 前提 | 議事録・決定・メモ・wiki・topics・deliverables・explorations・`tasks/`。タスクは 1 件 1 ファイル。一覧・状態を持つ場所が無い |
| `dxb-data-ai-workflow-context`（Kyo1M） | 本テンプレートの実運用 1 件目（5 月〜） | 議事録は定例ごとの 6 フォルダ＋直下（同じ日の議事録が最大 4 本）、決定 35、`tasks/` 47 件（active 24・done 11・superseded 12）。状態が各タスクの冒頭の「現在の状態」表と wiki 冒頭の「現在地」に分散し、週次の実施予定をタスクファイルで代用している |
| `analysis-project-template`（dxb-tech） | DXB 分析案件向け配布テンプレート。GitHub Copilot Chat 前提 | 議事録 6 列表・タスク登録の下書き・重い決定の判定・wiki 差分承認まで実装済み。台帳は無い |
| `analysis-template-dev`（dxb-tech） | 上記テンプレートの開発プロジェクト自身の情報管理 | 9/18 にタスク台帳 `docs/tasks/index.md` を新設し運用中。GitHub Issue・Project と連携し、`/task-issue`・`/task-breakdown` を試験中 |

### 1-2. 実運用で出ている困りごと

dxb-data-ai-workflow-context では次が起きている。

- タスクの一覧が無い。24 件の active タスクを把握するには各ファイルの冒頭を順に読むしかなく、AGENTS.md に「個別タスクは冒頭に最新状態を置く」「更新は議事録 → タスク冒頭 → 現在地 → 索引の順」という後付けの規則が増えた。
- 状態が 2 か所以上にある。タスク冒頭の「現在の状態」表と wiki 冒頭の「現在地」（長文化）と llms.txt の Open Tasks が同じことを別々に持つ。
- 「今週やること」の置き場が無く、`20260905_weekly-execution-plan.md`・`20260911_weekly-execution-plan.md` のような週次計画をタスクファイルとして作っている。
- 会議外（チャット・壁打ち）で出たタスクの出自が残らない。
- 議事録から起こすタスクの粒度が定まらず、推進テーマ単位のファイルに細かい行動まで書き足していく。

analysis-template-dev の台帳設計（9/18）が挙げた困りごと 3 つ（会議外のタスクの置き場が無い、開いているタスクの全体が見えない、議事録・詳細・Issue の紐付けが散らばる）のうち、前の 2 つと同じ問題である。

### 1-3. analysis-template-dev で育った仕組みと、本テンプレートでの扱い

| 仕組み | 内容 | 本テンプレートでの扱い |
|---|---|---|
| タスク台帳 | 進行中／完了の 2 節。列は ID・タスク・担当・期限・親・出典・詳細・状態 | 取り込む。ID は台帳の通し番号 `T-<n>`、状態は `未着手`／`進行中`（完了は完了節へ）に変える（Issue が無いため） |
| 議事録のネクストアクション表 | 5 列（#・担当・アクション・期限・登録先）。当日の記録で以後更新しない。子はサブ番号。担当・期限は「未定」 | 取り込む。「登録先」列の代わりに「台帳」列（台帳の ID）を置く |
| 保存前の確認 | 未定の担当・期限／親の提案などを 1 回の質問にまとめる | 取り込む。項目は 未定の担当・期限／親の提案／台帳の状態の変更／タスクファイルの `status: done` |
| 重い決定の判定 | 前提・定義・対象範囲・体制を変える決定だけファイル化。既存の決定と突き合わせる | 取り込む |
| wiki の「進行」表・「主な決定」表 | 差分案を出して承認後に反映 | 取り込む（「タスクのツール」「メンバー（GitHub ID）」行は持たない） |
| 承認レベルの分け | 自動: 議事録・台帳・llms.txt。承認: 決定ファイル・wiki | 取り込む。台帳の状態の変更は保存前の確認で承認 |
| 前回からの進捗・タスク登録の下書き | Issue の動きを議事録に載せる／起票用の文面を議事録末尾に置く | 取り込まない（Issue と連携しないため） |
| `/task-breakdown`・`/task-issue` | 壁打ちでタスクファイルを作る／Issue を起票する | skill は取り込まない。タスクファイルの型と壁打ちの手順だけ運用ガイドと AGENTS.md に書く |
| `scripts/task-ledger-status.sh` | Issue と Project の値を台帳の行の形で出す | 取り込まない |

## 2. 設計方針

1. **タスクの一覧と状態は台帳だけが持つ。** 議事録の表は当日の記録で以後更新しない。個別のタスクファイルは「台帳の 1 行に収まらない要件・仕様」だけに絞り、状態の節を持たせない。
2. **外部のタスク管理ツールとは連携しない。** 着手・完了は担当者が台帳を直し、会議で報告されたものは議事録作成時に AI が状態の変更を提案する。
3. **AGENTS.md は契約と要点、型の正本は `docs/guide/project-ops-guide.md`。** 議事録の構成・表の型・台帳の型・タスクファイルの型・決定の判定基準・wiki 差分の範囲・保存前の確認をガイドに置き、AGENTS.md はガイドを指す。skill は Step 0 で AGENTS.md → ガイドの順に読む。
4. **skill は規約駆動のまま Kyo1M/skills に置く。** テンプレートに skill 実体を持ち込まない。`meeting-minutes` の ID・状態・保存前の確認は、skill 側に値を固定せずガイドから読む。
5. **既存の型は温存し、追加中心にする。** 決定ファイルの ADR 4 節、`topics:` とトピックハブ、frontmatter lint、`tasks/` の位置は変えない。

## 3. 変更設計

### 3-1. テンプレート（project-context-template）

| # | ファイル | 変更 |
|---|---|---|
| A1 | `AGENTS.md` | ディレクトリ表の `tasks/` を「タスク台帳 `tasks/index.md`（一覧と状態）と、分量のある要件・仕様（1 タスク 1 ファイル）」に変更。「細かい日常タスク → GitHub Issues」の行を外す。frontmatter の `task` の必須 `assignee:`・`due:` を任意にする。推奨ワークフロー 1（議事録）の出力を「議事録・台帳追記と状態の反映・決定案（重い決定のみ）・llms.txt・wiki 差分」に書き換え、詳細はガイドへ委ねる。推奨ワークフロー 2（決定記録）に重い／軽いの基準と「主な決定」表を追加。推奨ワークフロー 3「タスク管理（台帳・タスクファイル）」を新設し、タスクファイルを壁打ちで作る手順を書く。推奨 skill 表を現行の自作 skill（meeting-minutes・grill-me・brainstorming・writing-plans・deck-outline・html-slide-deck・deck-critique）に更新。「正本と転写先の同期ルール」表を新設（小さく）。初期セットアップのヒアリング項目に 定例・議事録を作る人 を追加 |
| A2 | `tasks/index.md`（新設） | 台帳の雛形。frontmatter（`type: task`）、凡例（ID・状態・行を足す人）、空の「進行中」「完了」表 |
| A3 | `docs/wiki/index.md` | 「進行」表（現状／課題／体制／スケジュール／定例／議事録を作る人）、「主な決定」表、「用語」「未解決論点」「直近更新」を追加。「歩き方」「主要トピック」は維持 |
| A4 | `docs/guide/project-ops-guide.md`（新設） | 型の正本。1 どこに何があるか／2 議事録を作ると出るもの／3 タスクの持ち方（どこで見るか・着手と完了の書き方・親子）／4 型（議事録の構成・ネクストアクション表・台帳・決定・llms.txt と wiki の範囲・保存前の確認・タスクファイル）／5 議事録のフォルダ分け（`docs/minutes/<定例スラグ>/` を許容し、台帳は 1 つ）／6 棚卸し（仮置き: 四半期ごと、90 日更新無しの行を候補に） |
| A5 | `llms.txt` | 「Open Tasks」を台帳へのリンク 1 行に変更（個別列挙しない）。運用ガイドへのリンクを追加。「Decisions は全件、Recent Minutes は直近 5 件」の規則を書く |
| A6 | `README.md` | 早見表・日常運用フローを台帳前提に更新 |
| A7 | `scripts/lint-frontmatter.ts` | `docs/guide/*.md` をファイル名規則の対象外にする。`docs/superpowers/`（brainstorming・writing-plans の既定の置き場）と `docs/minutes/_drafts/`（走り書き）を lint 対象外にする。引用符なしの日付を YAML が Date に変えた場合も `YYYY-MM-DD` として検証する |

### 3-2. 台帳とネクストアクション表の型（要点）

型の正本はガイド 4 節。設計上の判断だけをここに残す。

| 項目 | 決め | 理由 |
|---|---|---|
| ID | 台帳全体の通し番号 `T-<n>`（最大値＋1。振った番号は変えない） | 会議日＋行番号の ID は、同じ日に複数の会議があると重なる（dxb-data-ai-workflow-context では 8/31 に 4 本）。定例ごとにフォルダを分けても台帳は 1 つで持てる |
| 状態 | `未着手`／`進行中`。完了・見送りは完了節へ（見送りはタスク名の末尾に「（見送り）」） | Issue が無いので、担当者が自分で直せる最小の語彙にする |
| 議事録の表 | `# | 担当 | アクション | 期限 | 台帳`。子はサブ番号（同じ議事録の行 2 の子は `2-1`、台帳の T-6 の子は `T-6-1`） | 表から台帳の行を 1 つで引けるようにする。表は当日の記録なので、ID は表を作るときに振る |
| 出典 | 議事録の行（行番号の無い古い議事録はリンクだけ）／`チャット`／`壁打ち`＋日付 | 移行時に以前の 3 列表の議事録も出典にできる |
| 状態の更新 | 担当者が台帳を直す。会議で着手・完了・見送りが報告されたら、`meeting-minutes` skill が保存前の確認で変更を提案する | 会議のたびに台帳が揃う。メモにはっきり無いものは提案しない |

### 3-3. skill（Kyo1M/skills）

| # | skill | 変更 |
|---|---|---|
| B1 | `meeting-minutes`（更新） | Step 0 のプロファイル項目に 台帳の場所と ID・状態の規則・決定一覧（llms.txt）・wiki 差分の範囲・承認レベル・保存前の確認の項目 を追加し、AGENTS.md が指すガイドを読む。Step 3 で議事録の表に台帳 ID を振り、保存前の確認を 1 回にまとめる。Step 4 の派生を「台帳追記（自動）と状態の変更（確認で承認）・決定判定（承認）・llms.txt（自動）・wiki 差分（承認）」にする。ID・状態の語彙・確認の項目は skill に固定せず、ガイドの規則に従う（ガイドが GitHub Issue 連携を定める repo では従来どおり前回からの進捗・下書きを扱う）。台帳の無いリポジトリでは現行の振る舞いを維持 |
| B2 | `README.md` | 管理表の `meeting-minutes` の説明を更新 |

### 3-4. 範囲外・後追い

- GitHub Issue・Project・外部ボードとの連携（起票・状態の同期・前回からの進捗）は本テンプレートでは持たない。必要な案件は analysis-project-template 側の仕組みを使う。
- `task-breakdown`・`task-issue` skill は本テンプレートの推奨 skill に入れない（Kyo1M/skills 側に置いたままにするか消すかは別に決める）。
- dxb-data-ai-workflow-context への適用は別作業。移行手順を書くときは次を初期値にする（仮置き）。
  - active のタスクファイル（推進テーマ）は台帳の親の行にする。ファイル冒頭の「現在の状態」表の「次の一手」は子の行にし、表はファイルから外す（履歴は git に残る）。「完了判断」は「完了条件」節へ移す。
  - done のファイルは完了節へ（完了日はファイルの最終更新日）、superseded のファイルは台帳に載せない。
  - 週次計画のファイル 2 件は、中身を台帳の子の行に畳み、ファイルは superseded にする。
  - wiki 冒頭の「現在地」は「進行」表と台帳へ分けて圧縮する。
  - 以前の議事録の表（3 列）は書き換えない。台帳の出典は議事録へのリンクだけにする。

## 4. 実装単位

| 単位 | 内容 | リポジトリ | 検証 | 依存 |
|---|---|---|---|---|
| P1 | テンプレートの型（A1〜A7） | project-context-template | `npm run lint --prefix scripts` が通る。Use this template 相当で作った空リポジトリに台帳・進行表・ガイドの参照がある | なし |

## 5. 確認したこと（2026-09-25 回答）

1. **台帳の置き場**: `tasks/index.md`（現行の `tasks/` のまま）。
2. **型の正本の置き場**: AGENTS.md は要点、型の正本は `docs/guide/project-ops-guide.md`。
3. **決定ファイルの見出し**: 現行の ADR 4 節（Context／Decision／Consequences／Alternatives Considered）を維持（仮置き。実運用の決定 35 件がこの形のため。ファイルにするのが重い決定だけになったので 4 節の分量に見合う）。別案がメモに無ければ Alternatives Considered は省き、推測で埋めない。
4. **`docs/superpowers/` の扱い**: lint 対象外にして残す。
5. **分析固有の持ち込み**: 本リポジトリはプロジェクト情報管理用のテンプレートで、analysis 系は分析プロジェクト用。移植時に分析固有のドキュメント・フロー（分析設計書・テーブル定義・SQL・Copilot プロンプト等）を持ち込まず、ガイドの例も分析に寄らない語にする。
6. **タスクの管理先**: GitHub Issue での管理は本テンプレートでは行わず、台帳とタスクファイルで管理する。
7. **task 系 skill**: `task-breakdown`・`task-issue` は本テンプレートに移行しない。

## 6. 前提と未確定

- 前提: 本テンプレートの利用者は Claude Code / Codex。Copilot 利用者は analysis-project-template を使う。
- 未確定: `meeting-minutes` の 1 回の出力が増えるので、トークン消費が増える。P2 の試用で消費量を見る。
- 未確定: 棚卸しの閾値（90 日）は仮置き。
- 未確定: この設計書は `docs/superpowers/specs/` にあり、テンプレートから作る案件にもコピーされる。マージ前に外すか、テンプレート開発用として残すかを決める。
