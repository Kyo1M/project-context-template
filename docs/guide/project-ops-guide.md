# 運用ガイド

プロジェクトの情報（テーマ・タスク・担当・期限・決定・残論点・用語）はこのリポジトリに置き、会議のたびに `meeting-minutes` skill を 1 回実行して更新します。GitHub Issue や外部ボードなどのツールは、使うかどうかをプロジェクトが選びます（ツールを使う場合も、タスクの進捗だけをツール側で持ちます）。

このガイドは **型の正本** です。`AGENTS.md` は要点と参照だけを持ち、skill（`meeting-minutes`・`task-breakdown`・`task-issue`）はこのガイドの型に従って動きます。型を変えるときは、このガイドを先に直してから `AGENTS.md`・`tasks/index.md` の凡例・`llms.txt`・`README.md` に写します。

| 読む人 | 読む節 |
|---|---|
| PM・議事録を作る人 | 全部 |
| メンバー（タスクを受け取る人） | 3 節（自分のタスクがどこに載り、着手・完了をどこで伝えるか） |

## 1. どこに何があるか

| 種別 | 正本 | 更新者 | 更新のきっかけ | AI の範囲 | 承認 |
|---|---|---|---|---|---|
| テーマ（目的・前提・対象外） | `docs/wiki/index.md` 概要・前提 | 議事録を作る人 | 初回セットアップ、以後は議事録作成時 | 差分案 | 差分を 1 回 |
| 進行（現状・課題・体制・スケジュール・タスクのツール・メンバー） | `docs/wiki/index.md`「進行」表 | 議事録を作る人 | 初回、以後は変更時 | 差分案 | 差分を 1 回 |
| タスクの一覧と状態 | `tasks/index.md`（タスク台帳） | AI（議事録作成時・起票時）、人（会議外のタスク） | 議事録作成時、起票時、会議外でタスクが出たとき | 追記・状態の写し | 自動（議事録と同じ PR で確定） |
| タスクの要件・仕様（本文に収まらないもの） | `tasks/yyyymmdd_<slug>.md` | 担当者（`task-breakdown` skill で壁打ち） | 分解・詳細化が要るとき | 壁打ちと清書 | ファイルごと |
| 会議の記録 | `docs/minutes/yyyymmdd_<slug>.md` | 議事録を作る人 | 会議のあと | 生成 | 議事録ごと（PR） |
| 決定 | 議事録の「決定事項」が正本。前提・定義・対象範囲・体制を変える決定だけ `docs/decisions/` に 1 ファイル。方針転換は `docs/wiki/index.md`「主な決定」表で追う | 議事録を作る人 | 議事録作成時 | 重い決定かの判定（理由付き）、ファイル案、主な決定表の差分案 | 決定ごと |
| 残論点 | `docs/wiki/index.md` 未解決論点 | 議事録を作る人 | 議事録作成時 | 追加・解消の差分案 | 差分を 1 回 |
| 用語 | `docs/wiki/index.md` 用語 | 議事録を作る人 | 議事録作成時 | 差分案。聞き取れていない用語の行は作らず、未解決論点に「定義を聞く」を置く | 差分を 1 回 |
| 思考メモ・壁打ち・資料 | `docs/memo/`・`docs/explorations/`・`docs/deliverables/` | 書いた人 | 随時 | 生成 | ファイルごと |
| トピックの横串 | `docs/wiki/topics/<slug>.md` | AI | 新規ファイルの commit 時、依頼時 | 再生成 | 差分を 1 回 |
| LLM 向け索引 | `llms.txt` | AI | 議事録作成時、ファイル追加時 | 追記 | 自動 |

「議事録を作る人」はプロジェクトごとに 1 人を決めて、wiki「進行」表の「議事録を作る人」行に書きます。確定は PR の差分確認とマージで行います（セルフマージ可）。

## 2. 議事録を作ると出るもの

`meeting-minutes` skill を 1 回実行すると、次が出ます。自動で反映してよいものと、承認してから反映するものを分けています。

| 出るもの | 置き場 | 反映 |
|---|---|---|
| 議事録（概要・前回からの進捗・決定事項・確認事項・ネクストアクション表・議事内容・メモ・タスク登録の下書き） | `docs/minutes/yyyymmdd_<slug>.md` | 自動（保存前の確認を 1 回だけ聞く） |
| タスク台帳への追記と、Issue の状態の写し | `tasks/index.md` | 自動 |
| 決定ファイルの案（重い決定だけ） | `docs/decisions/yyyymmdd_<slug>.md` | 承認してから |
| `llms.txt` の追記（Recent Minutes・Decisions） | `llms.txt` | 自動 |
| wiki の差分案（直近更新・進行・主な決定・未解決論点・用語） | `docs/wiki/index.md` | 承認してから |

人が決めるのは、保存前の確認（4-8）への回答、決定ファイル案の採否、wiki 差分案の採否の 3 つです。反映後、議事録・台帳・決定・`llms.txt`・wiki をまとめて 1 コミットにし、PR の差分確認とマージで確定します。GitHub Issue を使う案件では、コミットのあとに `task-issue` skill で起票します。

## 3. タスクのツールと動線

**タスクの一覧と状態はタスク台帳 `tasks/index.md` が持ちます。** 議事録の「ネクストアクション」表はその会議で出たタスクの記録で、作成後は書き換えません。ツールを使う案件では進捗の正本はツール側で、台帳には AI が写します。

### 3-1. ツールを 1 つ決めて wiki に書く

`docs/wiki/index.md` の「進行」表の「タスクのツール」行に、次の 3 つから 1 つを書きます。決めていない案件では、`meeting-minutes` skill が最初の実行時に 1 回だけ聞きます。

| 値 | 向いている案件 |
|---|---|
| `なし（表のみ）` | 少人数で、台帳を見れば足りる |
| `GitHub Issue（リポジトリ: <org>/<repo>、Project: <URL>）` | 作業が PR で流れており、タスクも GitHub で追いたい |
| `外部ボード（Teams ボード等）` | クライアントや PM がボード・WBS で管理している |

`GitHub Issue` の案件は、あわせて「メンバー」行に `名前: GitHub ID` を並べます（`task-issue` skill が担当を assignee に変換するのに使います）。

### 3-2. いまのタスクの一覧と、タスクの詳細はどこで見るか

| 見たいもの | ツールが `なし（表のみ）` | ツールが `GitHub Issue`／`外部ボード` |
|---|---|---|
| いま開いているタスクの一覧 | 台帳の進行中節。着手・完了は担当者が台帳の状態・完了日を直す | 進捗の正本はツール側（GitHub Issue なら Project のかんばん・ロードマップ）。リポジトリ内では台帳の進行中節（議事録作成時に AI が Issue の状態を写す）。前回会議日以降に閉じた・コメントで動いた・新しく立った Issue は、次の議事録の「前回からの進捗」節に AI が一覧で載せ、台帳にも写す |
| タスクの詳細（背景・やること・完了条件） | 分量のある要件は `tasks/yyyymmdd_<slug>.md`（`task-breakdown` skill が壁打ちで作る）。それ以外は議事録の「議事内容」の該当テーマ | Issue の本文・カードの説明。本文に収まらない背景・完了条件は `tasks/yyyymmdd_<slug>.md` に置き、Issue 本文の「詳細:」行からリンクする。Issue のコメントで中身が変わったら `task-breakdown` skill（Issue 番号を入口）で食い違いを見てファイル側を直す |

状態を持つのは台帳だけです。同じ状態を 2 か所で手で持つと片方が古くなるためで、ツールを使う案件では台帳の状態はツール側から写す一方向にします。会議の外（チャット・壁打ち）で出たタスクは台帳の進行中節に人が 1 行足します（ID は `yyyymmdd-#`、出典は `チャット`／`壁打ち`＋日付）。Issue にするなら `task-issue` skill を回します。

### 3-3. ツールごとの動線

| ツール | タスク登録の下書きをどうするか | 貼ったあと |
|---|---|---|
| `なし（表のみ）` | 何もしない。議事録と台帳に残す | 担当者が台帳の状態を直す（着手で `進行中`、終わったら完了日を書いて完了節へ） |
| `GitHub Issue` | `task-issue` skill を実行する。登録計画（タイトル・担当・親・期限・Project のフィールド）を承認すると、Issue 作成 → Sub-issue の紐付け → Project 取り込み → 台帳の書き戻し（ID を `#n`、状態を `登録済み`）まで行う。gh が無い環境では、出力された文面の見出しを Issue のタイトルに、本文を Issue の本文に貼る | `task-issue` skill が台帳の ID・状態を直す（手で貼ったときは人が直す）。以後の担当・期限・状態は議事録作成時に AI が Issue から写す |
| `外部ボード` | 下書きの見出しをカード名に、本文をカードの説明に貼る | 台帳の状態を `登録済み（カード名）` に直す。以後は人が直す |

- 台帳の状態を `登録済み` に直しておくと、`task-issue` skill が同じ行を二度起票しなくなります。
- 担当・期限が「未定」の行も下書きに含まれます。`task-issue` skill は期限が未定の行に「いつまでに決めるか」の日付を仮置きで提案します（ロードマップにバーを出すため）。
- 既にボードや WBS で管理している案件は、そのやり方を変える必要はありません。下書きは「ボードに貼る文面の下書き」として使ってください。
- タスクを受け取ったメンバーは、着手・完了をツール側（ツールが無い案件は台帳）で伝えます。議事録の表を自分で書き換える必要はありません。

### 3-4. 親子（タスクの分解）の付け方

議事録の 1 行は「誰かが動く単位」なので、着手すると数ステップに割れます。親子は次の 2 か所で付けます。

| どこで | 書き方 |
|---|---|
| 議事録のネクストアクション表 | `#` 列のサブ番号。同じ議事録の行 2 の子は `2-1`・`2-2`、前回以前に登録済みの Issue #6 の子は `#6-1`（Issue 番号には `#` を付け、行番号には付けない）。`meeting-minutes` skill が親候補を理由付きで提案し、保存前の確認で人が直す |
| `tasks/yyyymmdd_<slug>.md` | `task-breakdown` skill で壁打ちして「やること」を番号付きで書く。`task-issue` skill にこのファイルを渡すと各項目を子 Issue にする（親は frontmatter の `issue:`。無ければ親も作る） |

- 親の候補になるのは 3 つだけです: 同じ議事録の同じ小見出しから出た行、既存の open Issue、`tasks/` のファイルの「やること」の項目。これに当たらない行は子にしません。
- 階層は 2 段までにします。GitHub では Parent issue で親子を見るので、Issue のタイトルに番号は付けません。
- 連絡・回答・日程調整のように数日で終わり進捗を追う必要が無い行（報告する・回答する・共有する・セットする など）は、Issue にせず登録先を空欄（表のみ）にします。`meeting-minutes` skill が提案し、人が確認します。

### 3-5. GitHub Issue と Project の運用

- **登録先リポジトリと Project は wiki の「進行」表に書く。** 「タスクのツール」行を `GitHub Issue（リポジトリ: <org>/<repo>、Project: <URL>）` の形にし、「メンバー」行に `名前: GitHub ID` を並べます。
- **期限は仮でも必ず入れる。** 日付が空の Issue はロードマップにバーが出ず、存在しないのと同じになります。未定のタスクは「いつまでに決めるか」の日付を仮置きし、決まったら Issue 側で直します。
- **開始日は着手予定日。** 親（議事録の行）は会議日、子は着手予定日を入れると、ロードマップが週の並びとして読めます。
- **Status を動かすのは担当者。** 着手で In Progress、Issue を閉じたら Done（Project の Workflows で自動化できます）。
- **完了したタスクは議事録の表に書き戻さない。** 閉じた Issue・コメントで動いた Issue・議事録を経ずに立てた Issue は次の議事録の「前回からの進捗」節に AI が一覧で載せ、あわせて台帳の担当・期限・状態を写し、閉じた Issue の行を完了節へ移します。
- **GitHub 側の手直しが正本。** 作成後の親の付け替え・クローズ・期限変更・担当変更は GitHub の画面で行い、AI はそれを読むだけで書き換えません。リポジトリ側で AI が直すのは、台帳（Issue の状態の写し）、`tasks/yyyymmdd_<slug>.md` の frontmatter `status`（対にした Issue が閉じたとき、議事録作成の保存前の確認で提案）、`task-breakdown` skill の更新モード（ファイルと Issue 側の食い違いを表で見せ、採る側を確認してからファイルを直す）だけです。
- **Issue 本文の中身（やること・完了条件）を変えるときは `tasks/` のファイルを直す。** `task-breakdown` skill に Issue 番号を渡すと、Issue 側（本文・コメント・Sub-issue）とファイルの食い違いを表で見せ、採る側を確認してからファイルを直します。直したら Issue にコメントで一言（PR の URL）残します。

## 4. 議事録とタスク台帳の型（正本）

### 4-1. 議事録の構成

```markdown
---
type: minutes
title: <日本語タイトル>
date: "YYYY-MM-DD"           # 会議日
status: draft
topics: []
tags: []
attendees: []
meeting_type: kickoff | review | sync | ...
derived_from: [docs/minutes/_drafts/yyyymmdd_<slug>-memo.md]
related: []
---

# <日本語タイトル>

## 概要

## 前回からの進捗

## 決定事項

## 確認事項

## ネクストアクション

| # | 担当 | アクション | 期限 | 登録先 |
|---|------|-----------|------|--------|

## 議事内容

### <テーマ 1>

### <テーマ 2>

## メモ

## タスク登録の下書き
```

- 「概要」は 3〜5 行で、会議の位置づけと要点だけを書きます。
- 「議事内容」はテーマ別に小見出しを立て、そのテーマで出た意見・やり取り・検討したが決めなかったこと・残った論点を残します。決定事項・ネクストアクションに集約して途中の議論を削らないでください。テーマは会議の議題単位（メモの見出しがあればそれに従う）。
- 「メモ」は分類しにくい補足だけに使います。
- 「前回からの進捗」は動いた Issue が無ければ（ツールが GitHub Issue でない案件では常に）、「タスク登録の下書き」はネクストアクションの行が無ければ、節ごと省きます。
- 会議の日付・参加者が不明なときは「要確認」と書きます。ネクストアクションの担当・期限が決まっていないときは「未定」と書き、「要確認」は使いません。
- メモに無い事実・決定・担当・期限を作らないでください。生データ・個人情報・認証情報・実数値がメモに混ざっていたら、転記せずその旨を伝えます。

### 4-2. ネクストアクション表

| # | 担当 | アクション | 期限 | 登録先 |
|---|------|-----------|------|--------|
| 1 | PM | 対象範囲の定義をクライアントに確認する | 2026-09-18 | GitHub Issue |
| 1-1 | PM | 前回提案書の対象範囲の記述を洗い出す | 2026-09-16 | GitHub Issue |
| #6-1 | 分析担当 | 集計条件を定義に合わせて直す | 2026-09-25 | GitHub Issue |
| 2 | PM | 中間報告の日程をクライアントに連絡する | 2026-09-19 | |

- `#`: 議事録内の連番。子タスクはサブ番号で書く（同じ議事録の行 1 の子は `1-1`、前回以前に登録済みの Issue #6 の子は `#6-1`）。階層は 2 段まで。番号は議事録の中で親子を書くための記法で、GitHub 側では Parent issue で見る。
- 議事録をまたぐ同一性は台帳の ID で持つ。前回の議事録から未登録の行を引き継がない（未登録かどうかは台帳の状態列で分かる）。同じタスクが再び話題になったときは、新しい行を作らず台帳の担当・期限を直す。
- 表は会議当日の記録で、以後は書き換えない（状態列を置かない）。
- `担当`: メモにある人だけ。決まっていなければ「未定」。
- `アクション`: 40 字以内の動詞止め。「〜を確認する」「〜を検討する」も、誰かが動くものはここに置く（決定にはしない）。
- `期限`: `YYYY-MM-DD`。「次回まで」は次回の会議日が分かればその日付（wiki「進行」表の「定例」行から導ける場合は候補日として提案し、保存前の確認で示す）、分からなければ「未定」。
- `登録先`: wiki「進行」表の「タスクのツール」行の先頭のツール名。`なし（表のみ）` の案件は空欄。ツールを使う案件でも、連絡・回答系で数日で終わる行は空欄（表のみ）にしてよい（AI が提案し、人が確認する）。

### 4-3. タスク台帳

`tasks/index.md`。「進行中」「完了」の 2 節。

```markdown
| ID | タスク | 担当 | 期限 | 親 | 出典 | 詳細 | 状態 |
|---|---|---|---|---|---|---|---|
| #30 | 集計条件を定義に合わせて直す | 分析担当 | 2026-09-25 | #6 | [2026-09-17 議事録](../docs/minutes/20260917_<slug>.md) 行 #6-1 | | 登録済み |
| 20260918-1 | 新メンバー向けに運用の説明会を行う | PM | 2026-10-08 | | 壁打ち 2026-09-18 | [20260918_onboarding.md](./20260918_onboarding.md) | 未登録 |
```

- 完了節は `状態` の代わりに `完了日` を持ち、閉じた行を進行中節から移す。年をまたいで長くなったら `tasks/archive/<年>.md` に切る。
- `ID`: Issue があれば `#n`。別リポジトリの Issue は `<短い名前>#n` のようにリポジトリの短い名前を前置。起票前とツール無し案件は `yyyymmdd-#`（出典の日付＋その日の連番。子は `yyyymmdd-#-#`）。起票したら `task-issue` skill が `#n` に書き換える。
- `親`: 親の ID。2 段まで。
- `出典`: 議事録の行（リンク＋行番号）か、会議外なら `チャット`／`壁打ち`／`Issue 直接`（議事録を経ずに GitHub で立てた Issue）＋日付。
- `詳細`: `tasks/yyyymmdd_<slug>.md` があればリンク。
- `状態`: `未登録`（ツールを使う案件で、まだ起票していない行）／`表のみ`（ツールを使う案件で Issue にしない行と、ツールが `なし（表のみ）` の案件の全行）／`登録済み`（Issue あり。Project の Status が Todo）／`進行中`（In Progress）／`完了`（closed）。外部ボードの案件は `登録済み（カード名）`。見送り（not planned）で閉じたものはタスク名の末尾に「（見送り）」。
- 行を足すのは `meeting-minutes` skill（議事録の表の全行）・`task-issue` skill（起票時に ID と状態を更新。自由記述で起票したときは出典 `チャット` で行を足す）・人（会議外のタスク）。
- **GitHub Issue の案件では担当・期限・状態の正本は Issue・Project で、台帳には AI が写す**（議事録作成時に「前回からの進捗」を読むとき。closed は完了節へ、Status と assignee・期限フィールドで上書き、議事録を経ずに立った Issue は出典 `Issue 直接` で追記）。人が台帳の状態を直すのは `表のみ` の行とツール無し案件だけ。
- **Issue・Project 側は AI が読むだけで、書き換えない**（close・コメント・本文・フィールド・親子）。起票だけは `task-issue` skill が承認後に行う。

### 4-4. タスク登録の下書き

議事録末尾の「タスク登録の下書き」節に、ネクストアクション表の全行を置きます（登録先が空欄の行も含める。ツールを後から決めたときに貼れるように）。

```markdown
## タスク登録の下書き

### 対象範囲の定義をクライアントに確認する

- 出典: [2026-09-14 議事録](./20260914_<slug>.md) 行 1
- 台帳: 20260914-1
- 担当: PM
- 期限: 2026-09-18
- 登録先: GitHub Issue
- 詳細: [tasks/20260914_<slug>.md](../../tasks/20260914_<slug>.md)

提案書と定例の発言で対象範囲の記述が食い違っている。どちらを採るかをクライアントに確認し、wiki の前提に反映する。
```

- 見出しは表の「アクション」そのまま。番号は付けない（親子は GitHub の Parent issue で見る。台帳の ID は本文の「台帳:」行に書く）。
- 登録先が空欄の行は `- 登録先: 表のみ` と書く。
- 本文は 出典（行 n）・台帳（ID）・担当・期限・登録先 の 5 行に、子タスクなら「親: 行 n」または「親: Issue #n」、`tasks/` のファイルがあれば「詳細: <パス>」を足し、空行のあとに概要を 2〜3 行（そのテーマの「議事内容」から、何のために何をするか）。実数値・個人情報・認証情報は書かない。
- リンクは議事録からの相対パスのまま書く（Issue に載せるときの `main` の blob URL への展開は `task-issue` skill が行う）。

### 4-5. 前回からの進捗（GitHub Issue を使う案件だけ）

前回会議日（同じフォルダで会議日が直近の議事録の `date`）以降に動いた Issue を、「概要」の次、「決定事項」の手前に 1 Issue 1 行で載せます。拾うのは次の 3 群だけです。担当・期限・ラベル・Project フィールドの変更は Project 側で見えるので載せません。

| 群 | 判定 |
|---|---|
| 完了 | 前回会議日以降に closed |
| 更新 | open のまま、前回会議日以降に作られたコメントがある |
| 新規 | 前回会議日以降に作られ、台帳に ID が無い（議事録を経ずに立てた Issue）。親が登録済みの Issue なら親ごとに畳む |

```markdown
## 前回からの進捗

- 完了 #9 週 2 回の定例をセットする（9/14）
- 更新 #6 集計条件の見直し: コメントで対象を EC に絞る方針（9/15）
- 新規 #25 利用状況の調査計画を立てる（担当: PM）
- 新規 #3 の子: #15〜#18（担当: 分析担当）
```

- 「何が変わったか」は close 日・コメントの要点・担当を 1 行で。コメントの要約はコメントに書かれていることだけを書く。
- コメントに書かれた決定・方針変更は、議事録の「決定事項」に `（出典: Issue #n）` を付けて載せ、会議メモの決定と同じ判定（4-6）に乗せる。コメントの内容と会議メモが食い違うときは会議メモを採り、食い違いを確認事項に書く。
- 前回の議事録の表は書き換えない。完了・更新・新規の内容を台帳に写す。

### 4-6. 決定の判定と決定ファイル

議事録の「決定事項」を 1 件ずつ見て、`docs/decisions/` にファイルとして起こす「重い決定」かどうかを判定し、理由 1 文を添えて提示します。承認されたものだけ保存します。

- **重い決定（ファイルにする）**: プロジェクトの**前提・定義・対象範囲・体制**を変える決定。例: 対象範囲（EC のみに絞る）、定義（売上は税抜で数える）、体制（議事録を作る人を変える、レビューの回し方を変える）、前提（納期を 1 か月後ろにする）。
- **軽い決定（議事録の決定事項に留める）**: 進め方の確認・優先順位・次回の扱い・個別タスクの担当割りなど、前提・定義・範囲・体制が変わらないもの。
- 決定かどうか迷うもの（「〜を確認してから決める」など、まだ決まっていないこと）は決定にせず、ネクストアクションか確認事項に置く。メモに留保が付いた合意（「たぶん」「暫定」）は決定事項に留保を注記して載せ、確認事項に「次回冒頭で再確認」を置く。ファイルにするかは承認時に人が決める。
- 同じ決定が既に `docs/decisions/` にある（再確認・言い直し）ときは、新しいファイルを提案せず「既存の決定ファイル `<パス>` の再確認」と伝える。既存かどうかは `llms.txt` の「Decisions」（全件）と突き合わせる（直近の議事録だけでは 2 回以上前の決定を見落とす）。内容が変わる決定なら、既存ファイルを `status: superseded` にして新しいファイルを提案する（古いファイルは消さない）。
- 重い決定が 1 つもなければ「今回はファイルにする決定なし（軽い決定 n 件は議事録に記載）」と伝える。
- 重い決定は、決定ファイルの案とあわせて、wiki「主な決定」表に足す 1 行（日付・決定・効く先・出典）も示す。

決定ファイルは 1 決定 1 ファイル。`docs/decisions/yyyymmdd_<slug>.md`（日付は会議日）。

```markdown
---
type: decision
title: <決定の日本語タイトル>
date: "YYYY-MM-DD"
status: active
topics: []
tags: []
derived_from: [docs/minutes/yyyymmdd_<slug>.md]
related: []
drivers: []
alternatives_considered: []
supersedes: []
---

# <決定の日本語タイトル>

## Context
なぜ判断が必要になったか、背景

## Decision
何を決めたか（1〜3 文）

## Consequences
この判断によって生じる帰結（良い面・悪い面）

## Alternatives Considered
検討した別案と却下理由（メモに出てこなければ節ごと省略）
```

### 4-7. llms.txt と wiki の更新範囲

| 対象 | 何を | 反映 |
|---|---|---|
| `llms.txt` | 「Recent Minutes」に作成した議事録の 1 行リンク（直近 5 件程度に整理）。決定ファイルを保存したら「Decisions」に 1 行（全件。間引かない）。「Open Tasks」は台帳へのリンク 1 行のまま（個別列挙しない） | 自動 |
| `docs/wiki/index.md` | 「直近更新」への 1 行（新しい順に先頭へ。次に参加する人が知るべき変化だけ）。決定・議論で前提・進行（現状・課題・体制・スケジュール）・未解決論点・用語に変化があればその差分（解決した論点の削除・新しい論点の追加。「進行」表の行が空なら今回の内容から埋める案を出してよい）。重い決定があれば「主な決定」表への 1 行。タスクのツールを聞いたときは「進行」表への行の追加。台帳や wiki の各表に今回の議事録と矛盾する行や 90 日以上更新の無い行があれば「棚卸し候補」として一覧を添える（消さない） | 変更前 → 変更後の差分の形で提示し、承認されたものだけ反映。承認前に書き換えない。候補を増やしすぎない |

### 4-8. 保存前の確認

議事録を保存する前に、次の 4 つを 1 回の質問にまとめて聞きます。該当が無い項目は省きます。

1. **担当・期限が未定の行**: 番号で列挙し、その場で埋めるか次回の確認事項に回すかを聞く。「次回に回す」の行は「未定」のままにし、「確認事項」に「n・n-1 の担当・期限を次回に決める」を 1 行足す。
2. **親の提案**: サブ番号を付けた行と、その理由（同じ小見出し／open Issue #n／`tasks/` の項目）。違えば親を外すか付け替える。
3. **登録先を空欄にする提案**: 連絡・回答系で表だけに残す行。Issue にしたい行があれば戻す。
4. **`tasks/yyyymmdd_<slug>.md` の `status` を `done` にする提案**（GitHub Issue の案件だけ）: 完了群の Issue の URL と frontmatter `issue:` が一致するファイル。「やること」の子が全部閉じていても、親の `issue:` が open なら提案しない。

wiki に「タスクのツール」行が無い案件では、項目の有無にかかわらず「タスクをどのツールで追いますか（なし（表のみ）／GitHub Issue／外部ボード）」を 1 問足します。回答を登録先列に使い、wiki 差分案に「タスクのツール」行の追加（GitHub Issue ならリポジトリと Project の URL、メンバー行も）を含めます。答えが無ければ `なし（表のみ）` とみなします。

### 4-9. タスクファイル（`tasks/yyyymmdd_<slug>.md`）

Issue や下書きの本文に収まらない要件・仕様の置き場。`task-breakdown` skill が壁打ちで作ります（日付は作成日。Issue 番号はファイル名に使わない）。

```markdown
---
type: task
title: <日本語タイトル>
date: "YYYY-MM-DD"
status: active            # 対にした Issue が閉じたら done（meeting-minutes skill が提案し、承認後に直す）
topics: []
tags: []
issue: <対にする Issue やカードの URL。無ければ空（task-issue skill が埋める）>
derived_from: []
related: []
---

# <日本語タイトル>

## 目的
このタスクが終わると何ができるようになるか（得られる状態で書く）

## 背景
今なぜ必要か。何ができていなくて、何が妨げられているか

## やること
1. <項目。1 人が数日で終えられる単位。起票済みは末尾に（#n）>
2. <項目>

## 完了条件
- <やること 1 に対応。検証できる行動で書く>

## 判断の観点
進めながら決めることがあれば、何を見て判断するか

## 制約・分かっていること

## 未確定事項
1. <質問>（誰に聞けば決まるか）
```

書くことが無い節は省きます。保存したら台帳の該当行の「詳細」列にリンクを足します（行が無ければ進行中節に 1 行足す）。

## 5. 議事録のフォルダ分け

定例が複数ある案件は `docs/minutes/<定例スラグ>/` に分けてよい（例: `docs/minutes/client-sync/`、`docs/minutes/internal-weekly/`）。分けたら `AGENTS.md` の「ディレクトリの選び方」表に 1 行足します。`meeting-minutes` skill は「同じフォルダで会議日が直近の議事録」を前回の議事録として読むので、定例ごとに前回会議日と進捗が追えます。走り書きは分けずに `docs/minutes/_drafts/` に置いて構いません。

## 6. 棚卸し

四半期ごと（案件の開始・中間・終了に相当）に、wiki の各表と台帳の進行中節を見直します。`meeting-minutes` skill は議事録作成時に、今回の議事録と矛盾する行と 90 日以上更新の無い行を「棚卸し候補」として返すだけで、消しません（閾値の 90 日は仮置き）。矛盾は新しい情報を正とし、古い行は消すか superseded の注記を付けます。担当は議事録を作る人です。メンバーが替わるときは「進行」表の体制・メンバー・議事録を作る人の行を新しい担当に書き換えます。
