# データ定義のガイド

分析案件で使うテーブルの定義と指標の定義を、YAML でリポジトリに残すときの **型の正本** です。テーブル定義は `docs/tables/<slug>.yaml`、指標の定義は `docs/metrics/<slug>.yaml` に置きます。分析をしない案件は読まなくて構いません。

`table-definition` skill と `metric-definition` skill（[Kyo1M/skills](https://github.com/Kyo1M/skills)）はこのガイドの型を読んで動きます。skill が無い環境でも、AI はこのガイドの型と各章の「作る流れ」に従って同じ YAML を作ります。型を変えるときは、このガイドを先に直してから `AGENTS.md` の要約と skill の既定の型（`table-definition/references/table-schema.md`・`metric-definition/references/metric-schema.md`）に写します。

| 知りたいこと | 読む章 |
|---|---|
| どちらの YAML にも共通する決まり | 1 章 |
| テーブルの粒度・キー・列・注意点の書き方 | 2 章 |
| 指標の式・分子と分母・母集団・束ね方の書き方 | 3 章 |
| 初めて使う案件で、置き場をどう足すか | 4 章 |

## 1. 共通の決まり

- **1 論理テーブル 1 ファイル、1 指標 1 ファイル。** ファイル名は日付を付けない `<slug>.yaml`。`slug` は英語の kebab-case（ASCII）で、YAML の `name` と同じにします。
- **詳細は YAML、一覧は wiki。** テーブルは `docs/wiki/index.md` の「データ」表、指標は「用語」表に 1 行ずつ載せ、その行から YAML へリンクします。
- **`status` は AI の案が `draft`。** 人が原本と見比べたり突き合わせを確かめたりしたら、人が `active` に変えます。
- **値・ID・件数は書きません。** 件数・欠損率・最小・最大などの数値プロファイルや値のサンプル、突き合わせた結果の数値は、定性で書きます（「年齢列はほぼ欠損」「月末の扱いでずれた」）。会話の中でも読み上げません。閾値と区分の切れ目（「45 時間以上」「5 回以上」）は事業上の決めごとなので書いて構いません。
- **分からない項目は「要確認」と書き、推測で埋めません。** どの取り方を正とするかは担当者が決めます。
- **保存と wiki の反映は承認してから。** YAML は 1 つずつ案を示し、承認されたものだけ保存します。wiki は変更前 → 変更後の差分で示し、承認されたものだけ反映します。`llms.txt` の 1 行の追記は索引の更新なので、承認を待たずに行います。
- **原本はコミットしません。** 定義書の Excel とそれを Markdown に生変換したファイルは `docs/references/` に置きます（`.gitignore` 済み）。
- **YAML の `derived_from` は md の frontmatter と書き方が違います。** 定義書は `docs/references/` のパスではなくファイル名とシート名、参考にした SQL はリポジトリ相対パス、説明から作ったものは「口頭」と書きます。手元にしかない原本のパスは書きません。
- **読むファイルを広げません。** 担当者が指定したファイルと、このガイド・wiki の表・既存の YAML だけを読みます。足りない定義は探しに行かず「要確認」として並べ、案を出す前にまとめて 1 回で聞きます。
- YAML は frontmatter の lint の対象外です（lint は md と html だけを見ます）。

## 2. テーブル定義の型

分析で使うテーブルの **構造**（何のテーブルで、1 行が何を表すか、主なキーは何か、どんな列があり、他のテーブルとどうつながり、使うときに何に気をつけるか）を書きます。国別・年別など同じ構造の物理テーブルが複数あるときは、1 つの論理テーブルにまとめて `physical_names` に列挙します。

### 2-1. YAML の型

記載例を兼ねます（架空の受注明細）。自分の案件に翻訳して使ってください。

```yaml
type: table                    # 種別（固定）
name: order-detail             # ファイル名と同じ slug（ASCII）
title: 受注明細                 # 日本語名
date: "YYYY-MM-DD"             # 作成・最終更新日
status: draft                  # AI 案=draft、原本と見比べ済み=active（人が変える）
derived_from:                  # もとにした定義書（配列）。口頭説明なら「口頭」、貼り付けなら「貼り付けの DDL」
  - sample_table_definition.xlsx の「列定義」シート
physical_names:                # 物理テーブル名（同じ構造が複数あれば列挙）
  - orders_jp
  - orders_tw
grain: 受注明細 1 行（1 注文 × 1 商品）   # 1 行が何を表すか
keys:
  primary: [order_id, line_no] # 一意性を決める列
  join: [customer_id, item_id] # 他テーブルとの結合に使う列
columns:                       # 列定義。定義書に無ければ空にして notes に「要確認」
  - name: order_id
    logical_name: 注文番号
    type: STRING               # 使うエンジンの物理型をそのまま
    nullable: false
    description: 注文単位の識別子
    note: ""                   # 使うときの注意（欠損が多い、コード値のまま、など）
  - name: order_date
    logical_name: 受注日
    type: DATE
    nullable: false
    description: 受注した日
    note: 締め処理の都合で月末分が翌月 1 日に入ることがある（要確認）
  - name: customer_id
    logical_name: 顧客 ID
    type: STRING
    nullable: true
    description: 会員の識別子
    note: 非会員は空
  - name: amount
    logical_name: 金額
    type: NUMERIC
    nullable: false
    description: 税抜の売上金額（現地通貨）
    note: 返品は負の値
relations:                     # 他テーブルとの参照関係
  - column: customer_id
    references: customer-master.customer_id
    cardinality: 多対1
    note: 非会員は customer_id が空
notes:                         # テーブル全体の注意点・集計時の前提
  - 返品は数量・金額が負で入る。正売上と返品額を分けて集計する
  - 通貨は現地通貨。円換算は為替マスタの換算方向を確認してから
```

### 2-2. 項目の書き方

| 項目 | 何を書くか |
|------|-----------|
| `status` | AI が案を出した時点は `draft`。原本と見比べて問題なければ人が `active` に変える |
| `derived_from` | もとにした定義書のファイル名（とシート名）の配列。口頭説明から作った場合は「口頭」、貼り付けなら「貼り付けの DDL」 |
| `physical_names` | 実際のテーブル名。同じ構造が複数あればすべて列挙する |
| `grain` | 1 行が何を表すか（「1 会員・1 日」「1 注文 × 1 商品」など） |
| `keys` | `primary` は一意性を決める列、`join` は他テーブルとの結合に使う列 |
| `columns` | 列ごとに物理名・論理名・型（使うエンジンの物理型をそのまま。BigQuery なら STRING・INT64 など）・NULL 可否・説明・注意 |
| `relations` | この列がどのテーブルのどの列を参照するか、多対 1 などの関係、注意 |
| `notes` | テーブル全体の注意点と集計時の前提。知らないと後で集計を作り直すことになりやすい情報（欠損が多い、重複しやすい、更新タイミングがずれる、対象外レコードが混ざる、換算方向が未確認、など）。定義書に無くても担当者に一言確認する |

**分からない項目**: 文字列の項目（`grain`・`type`・`description`）は「要確認」。配列の項目（`keys.primary` など）は空配列にして、`notes` に「主キーは要確認（store_code・sales_date で一意か）」のように 1 行置きます。参照先が分からない `relations` は行を作らず、`notes` に書きます。列の `note` は注意が無ければ空文字でよい。テーブル名や NOT NULL 列からの見立て（粒度・主キーの候補）は書いてよいですが、「（見立て。要確認）」を付けます。定義書の中の表記のぶれ（同じ列が別名で出る等）も `notes` に「要確認」として残します。

### 2-3. 生変換した Markdown（Excel）の読み方

定義書が Excel なら、原本を `docs/references/` に置き、Markdown に生変換してから読みます（例: `markitdown "docs/references/<定義書>.xlsx" -o docs/references/<名前>-raw.md`。変換ツールが無ければ、必要なシートを CSV に書き出すか列名の一覧を貼ってもらう）。

- 表題行・空行は `Unnamed: n` の見出しや `NaN` として残るので読み飛ばし、「列名」「物理名」「カラム名」「型」「論理名」などが並ぶ最初の行をヘッダとみなします。
- シートの役割を見分けます。テーブルの一覧（物理名・論理名・概要が並ぶ）は論理テーブルの候補と `physical_names`、列定義のシートは `columns`、結合設計・キーのシートは `keys`・`relations`・`notes`。検品結果や値が並ぶシートは読みません。
- 1 シートに同じ構造の物理テーブルが複数まとまっていたら、1 つの論理テーブルとして `physical_names` に列挙します。

### 2-4. wiki と llms.txt への載せ方

`docs/wiki/index.md` の「データ」節（「用語」の次）に、1 論理テーブル 1 行で載せます。データ列から YAML へリンクし、主キーが未確認なら「要確認（結合: …）」と書きます。

```markdown
## データ

| データ | 粒度 | 主なキー | 注意点 |
|--------|------|----------|--------|
| [受注明細](../tables/order-detail.yaml) | 1 注文 × 1 商品 | order_id, line_no（結合: customer_id, item_id） | 返品は負の値。円換算の方向は要確認 |
```

`llms.txt` の「Data」節には `- [受注明細](./docs/tables/order-detail.yaml): 1 注文 × 1 商品` の形で 1 行足します。

### 2-5. 作る流れ

1. **入力を確認する**: テーブル定義書（Excel・DDL・CSV のヘッダ・画面のコピー）があるかを聞く。無ければ担当者の説明からでも同じ型に落とせる。使うエンジン（BigQuery・Snowflake・PostgreSQL など）が wiki に無ければ 1 回聞く。
2. **対象を絞る**: テーブルが多いときは一覧（論理テーブル名・粒度・物理名）を出し、今回 YAML にするテーブルを合意する。分析で使う見込みの無いテーブルまで作らない。
3. **1 テーブルずつ案を出す**: 2-1 の型で示す（一度に全部埋めて渡さない）。
4. **保存する**: 承認された YAML だけを `status: draft` で保存し、原本と見比べたら `active` にするよう伝える。
5. **想定する集計ができるか確かめる**: 分析設計やタスクファイルに集計の論点があれば、この粒度・キーで集計できそうかを一言確認し、難しければ `notes` に残す。
6. **wiki と索引に反映する**: 2-4 の行を差分で示して承認後に反映し、`llms.txt` に 1 行足す。

定義書が更新されたら同じ流れで差分更新します（`date` を更新し、変わった列だけ直す）。

## 3. 指標の定義の型

分析で使う指標の **計算方法**（何をどう数えるか、分子と分母、対象に含める条件、期間や区分でまとめるときの取り方）を書きます。分析の計画・集計のクエリ・レビューが同じ定義を見るようにして、同じ指標を集計ごとに違う取り方で計算するのを防ぎます。指標の値そのものは扱いません。

### 3-1. YAML の型

記載例を兼ねます（架空の購入転換率）。自分の案件に翻訳して使ってください。

```yaml
type: metric                  # 種別（固定）
name: purchase-conversion-rate  # ファイル名と同じ slug（ASCII の kebab-case）
title: 購入転換率
aliases: [CVR]                # 資料・クライアント・SQL の列名での呼び名（任意）
date: "YYYY-MM-DD"            # 作成・最終更新日
status: draft                 # AI 案=draft。突き合わせが済んで人が確かめたら active（人が変える）
category: 売上                 # 指標の分類（任意。案件の KPI の分け方にそろえる）
derived_from:                 # もとにしたもの（定義書のファイル名とシート名／参考にした SQL のパス／「口頭」）
  - analysis/sql/monthly-conversion.sql
  - sample_metric_definition.xlsx の「KPI 定義」シート
definition: 購入者数 ÷ 訪問者数 × 100。月は訪問日・受注日の暦月。返品だけの注文は購入に数えない
numerator: 購入者数（その月の訪問者のうち、その月に受注日がある注文を 1 件以上持つ会員のユニーク数。返品だけの注文と非会員の注文は含めない）   # 率の指標だけ
denominator: 訪問者数（その月にログインして訪問した会員のユニーク数）   # 率の指標だけ
unit: percent                 # count | people | percent | ratio | currency | score | days | months | years
scale: 100                    # 率の指標だけ（100 なら %、1 なら比）
grain: 月                      # 1 つの値が何の単位で決まるか
keys: [month]                 # grain を表す列（集計の出力の列名）
time_key: month               # 期間の列
# window: 直近 12 か月         # 窓がある指標だけ（任意）。この指標には窓が無いので書かない
population: 期間内にログインして訪問した会員（退会者・社員アカウントを除く）
tables: [web-sessions, order-detail, customer-master]  # docs/tables/ の slug
polarity: higher_is_better    # higher_is_better | lower_is_better | neutral
basis: ratio_of_sums          # 粒度より粗い単位（期間・区分）にまとめるときの束ね方（3-3）
bands: []                     # 区切りを持つ指標だけ（任意。3-5 の記載例）
checks:                       # 別の出どころとの突き合わせ。結果は定性的に書き、件数は書かない
  - against: クライアントの月次レポートの CVR
    result: 訪問の数え方の違いでずれた（レポートは非ログインの訪問も分母に入れている）。違いを notes に残し、こちらの定義を正とした
    checked: "YYYY-MM-DD"
notes:
  - 月ごとの率を平均した値とは一致しない。四半期・年で見るときは、購入者数・訪問者数を四半期・年で数え直してから割る（月の人数を足さない）
```

### 3-2. 項目の書き方

| 項目 | 何を書くか |
|---|---|
| `status` | AI が案を出した時点は `draft`。`checks` の突き合わせが済み、人が確かめたら `active`。突き合わせ先が無い指標は `checks` に `against: なし（理由）` と書き、人が定義を確かめたら `active` にしてよい。突き合わせで合わないときは理由が分かるまで `draft` のまま |
| `derived_from` | もとにした定義書（ファイル名とシート名）・参考にした SQL のパス・「口頭」。複数あれば列挙する。正とした取り方の SQL があれば、そのパスを先頭に書く |
| `definition` | 1 行の式か数え方。あわせて、期間に入れる日付の列（受注日か出荷日か）、基準日（いつ時点の値か、起点の日）、通貨、税込か税抜か、返品の扱いのように、取り方で値が変わる決めごとを書く。SQL のコメントにしか無い決めごとも、ここか `notes` に移す |
| `numerator`・`denominator`・`scale` | 率の指標だけ。分子・分母はそれぞれ何をどの条件で数えるか（ユニーク数か件数か）まで書く |
| `unit` | 3-1 の値から選ぶ。通貨の種類は `definition` に書く |
| `grain`・`keys`・`time_key` | 指標の値が決まる単位と、それを表す集計の出力の列名。会員ごとの値なら「会員×年」、率なら「月」「店舗×月」のように、値が 1 つに決まる単位にする |
| `population` | 対象に含める条件と除く条件。wiki の「用語」表に定義がある条件（社員アカウントの除外など）は、その用語を名指しして参照する |
| `tables` | 使うテーブルの `docs/tables/` の slug（2 章）。定義が無いテーブルは「要確認」と書き、先にテーブル定義を作ることを勧める |
| `basis` | 3-3 の 6 つから 1 つ。中央値なども並べて出すときは `notes` に書く |
| `bands` | 指標そのものの区切り（回数の区分、金額の帯など）。区切りの名前（`label`）と条件（`rule`）を書く。区分の切れ目の正本はここで、wiki の区分の行はこの YAML へリンクする |
| `checks` | 別の出どころ（クライアントのレポート・定義書の値・既存の SQL の出力）と突き合わせた結果。結果は定性的に書く。確認クエリは保存しない（要点を `result` に書く）。後に回すときは `checks: []` |
| `notes` | 使うときの注意（採らなかった取り方、旧定義との違い、クライアントの集計との違い、束ねたときの読み方） |

**変種の扱い**: 同じ指標で取り方が違うものがどちらも使われる場合（現地通貨と円、税込と税抜など）は、別の slug にします（例: `annual-sales-local`・`annual-sales-jpy`）。片方だけを正にする場合は、もう片方を `notes` に「採らなかった取り方」として残します。

### 3-3. 束ね方（basis）

| basis | 束ね方 | 例 |
|---|---|---|
| `ratio_of_sums` | 分子・分母をそれぞれ束ねる単位で取り直してから割る（合計できるものは合計し、ユニーク数は数え直す） | 転換率、達成率、前年比 |
| `sum` | 合計 | 売上、受注件数 |
| `recount` | 粗い単位で数え直す（足さない） | 購入者数・会員数などのユニーク数 |
| `snapshot` | 期間の最後の時点の値 | 在籍数、期末の会員数 |
| `weighted_avg` | 件数などで重みを付けた平均 | アンケートの点数 |
| `simple_avg` | 単純な平均 | 会員ごとの購入回数の平均、元データに分子・分母が無く率だけがある指標 |

- 率の指標は分子・分母を取り直してから割り、月ごとの率を平均しません。月ごとの率の平均を使うときは、使う側（集計のコメント・分析設計）にそう書きます。
- ユニーク数は月の値を足さず、束ねる単位で数え直します（月ごとの購入者数の合計は、年の購入者数になりません）。率の分子・分母がユニーク数のときも、束ねる単位で数え直してから割ります。

### 3-4. wiki と llms.txt への載せ方

`docs/wiki/index.md` の「用語」表に、1 指標 1 行で載せます。用語の列を YAML へのリンクにし、定義の列には 1 行の式と束ね方だけを書きます。区分（回数の区分など）の行がすでにあれば、定義の列を YAML の `bands` へのリンクに置き換えます。YAML へリンクした行の正本は YAML です。会議などで定義が変わったら、議事録ではネクストアクションに「指標の定義の YAML を直す」を置き、この章の流れで YAML を直してから行を合わせます。

```markdown
| 用語 | 定義 |
|------|------|
| [購入転換率](../metrics/purchase-conversion-rate.yaml) | 購入者数 ÷ 訪問者数 × 100（束ね方: 分子・分母を数え直してから割る） |
```

`llms.txt` の「Metrics」節には `- [購入転換率](./docs/metrics/purchase-conversion-rate.yaml): 購入者数 ÷ 訪問者数 × 100` の形で 1 行足します。

### 3-5. 記載例 2（区分を持つ指標）

会員ごとの値を区分で束ねる指標の例です（架空の年間購入回数）。

```yaml
type: metric
name: annual-purchase-count
title: 年間購入回数
aliases: [購入頻度, F]
date: "YYYY-MM-DD"
status: active
category: 顧客
derived_from:
  - analysis/sql/customer-yearly-summary.sql
  - 口頭（年の区切りと返品の扱い）
```

### 3-6. 作る流れ

1. **何を作るかを伝える**: 指標の定義は式・分子と分母・対象・束ね方を 1 指標 1 ファイルで書いたもので、集計とレビューが同じ定義を見るためのものだ、と 2 行で示す。
2. **入力を選ぶ**: 次の 3 つのどれから起こすかを聞く。
   - (A) 既存の SQL: その指標をよく使う SQL・正だと思う SQL を 2〜3 本指定してもらう。SQL の置き場は `AGENTS.md` の「プロジェクト固有の指示」などの規約が指す場所で、リポジトリに無い SQL は貼ってもらう。指定が無ければ、置き場を指標名（日本語名・列名の候補）で grep して該当行のある SQL の一覧を出し、どれを読むかを 1 回で確かめてから読む。SQL のフォルダを順に開かない。
   - (B) 指標定義書: Excel なら 2-3 と同じく `docs/references/` で生変換して読む。値が並ぶシート（実績表など）は読まない。
   - (C) 分析設計・担当者の説明: 分析設計の指標の一覧を読むか、数え方を口頭で聞く。
3. **対象を絞る**: 候補の指標を一覧（指標名・出てくる SQL か資料・取り方が割れているか）にし、今回 YAML にするものを合意する。最初は 2〜3 個にする（一度に増やすと取り方の割れを確かめきれない）。`llms.txt` の「Metrics」節に同じ指標があれば、その YAML を読んで差分更新にする。
4. **1 指標ずつ案を出す**: 3-1 の型で 1 つずつ示す（一度に全部埋めて渡さない）。(A) では、同じ指標の取り方が SQL によって違う箇所（数え方・除外条件・日付の列・基準日・通貨）を表で並べ、どれを正とするかを担当者に聞く。使うテーブルの定義が `docs/tables/` に無ければ、先に 2 章のテーブル定義を勧める（無いまま進めるなら `tables` に「要確認」）。
5. **突き合わせ先を決める**: 突き合わせ先（クライアントのレポート・定義書の値・既存の SQL の出力）を担当者と決め、そのまま実行できる確認クエリを会話の中で示す（保存しない）。実行は担当者が分析環境で行い、「一致した」「どの期間・区分で、どちら向きにずれた」の形で結果を聞いて `checks` に書く。
6. **保存する**: 承認された YAML だけを `docs/metrics/<slug>.yaml` に `status: draft` で保存し、突き合わせが済んで確かめたら `active` にするよう伝える。
7. **wiki と索引に反映する**: 3-4 の行を差分で示して承認後に反映し、`llms.txt` に 1 行足す。

定義書や決めごとが変わったら、同じ流れで差分更新します（`date` を更新し、変わった項目だけ直す。食い違いは `notes` に書く）。

## 4. 初めて使うときに足すもの

テンプレートには `docs/tables/`・`docs/metrics/` を最初から置いていません。分析案件で初めてテーブル定義・指標の定義を作るときに、次をまとめて 1 回で承認を取ってから足します。

| 足すもの | テーブル定義 | 指標の定義 |
|---|---|---|
| 置き場 | `docs/tables/`（最初の YAML と一緒に作る） | `docs/metrics/`（同じ） |
| `docs/wiki/index.md` | 「データ」節（2-4 の表。「用語」の次）と、「歩き方」表に 1 行（使うテーブルの定義 → `docs/tables/`） | 「用語」表はそのまま使う。「歩き方」表に 1 行（指標の定義 → `docs/metrics/`） |
| `llms.txt` | 「Data」節（「Wiki」の次） | 「Metrics」節（「Data」の次） |

`AGENTS.md`・`README.md` のディレクトリ構造・置き場の選び方・命名・frontmatter の扱いには、`docs/tables/`・`docs/metrics/` が最初から書いてあるので、書き足しません。
